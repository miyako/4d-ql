# 4D Quick Look

[English](README.md) | 日本語

Finder で 4D 独自形式のファイルを Quick Look プレビューするための拡張機能です。
ファイルを選択してスペースキーを押すと、汎用アイコンではなくファイルの中身が表示されます。

| ファイル | プレビューの内容 |
|---|---|
| `.4DD` データファイル | レコード数順のテーブル一覧（上位 8 件、残りは「Other」にまとめて表示）、フィールド型、ストラクチャと一致する必要のあるデータベース UUID、並べ替え・検索言語とワイルドカード規則、インデックスエンジンのバージョン、ジャーナルファイルのパス、ストレージ使用量、正常に閉じられたか修復が必要か、[暗号化されたデータファイル](https://developer.4d.com/docs/commands/encrypt-data-file)の場合はどのテーブルが暗号化されているか |
| `.4DB` バイナリストラクチャ | フィールド数順のテーブル一覧、フィールド型、リレーション数、データベース UUID、並べ替え・検索設定、ジャーナル |
| `.4DCatalog` XML カタログ | テーブル・フィールド型・主キー・非表示フィールド・リレーションを図で表示。件数、データベース UUID、並べ替え・検索言語、スキーマ、暗号化可能テーブルは「Catalog details」に格納 |
| `.4DSettings` 設定ファイル | インデントと改行を保持したシンタックスハイライト付き XML ソース |
| `.4DLink` データベースショートカット | インデントと改行を保持したシンタックスハイライト付き XML ソース |
| `.4DPreferences` 環境設定ファイル | インデントと改行を保持したシンタックスハイライト付き XML ソース |
| `.4si` 読み込み・書き出し設定 | 順序どおりに並んだフィールドカード（読みやすい型表示付き）、サマリーカード、枠なしの設定とオプション |
| `.4DProject` プロジェクトファイル | インデントと改行を保持したシンタックスハイライト付き JSON ソース |
| `.4df` 保存されたクエリ | テーブル・フィールド番号、比較演算子、AND/OR/EXCEPT の接続子、保存された値、セレクションの出力先を条件カードで表示。元の JSON は下に折りたたみ表示 |
| `.4st` 保存されたセット | 選択レコード数、アドレス範囲に対するカバー率と分布、連続するレコード番号の範囲、保存されたカレントレコード。空ページ・全選択ページの圧縮もデコード |
| `.4qr` クイックレポート | リスト・クロス集計のデザインテンプレート（保存された幅、タイトル、フォント、色、罫線、ヘッダー・フッターのテキスト、並べ替え、小計、総計）。データベースや 4D ランタイムは不要 |
| `.4lbp` ラベル | ネイティブ XML のラベルデザインとシートレイアウト、保存されたテキスト、図形、ラスター画像、印刷順、余白、間隔、プロジェクトのテーブルフォーム参照 |
| `.4wp` 4D Write Pro ドキュメント | 用紙サイズ、余白、セクション、段組み、改ページ・セクション区切り、ヘッダー・フッター（先頭・左・右ページ）、段落・文字スタイル、リスト、タブ位置、表（データソースのテンプレートを含む）、インライン・アンカー画像、テキストボックスをページ単位で描画し、フォーミュラは参照として表示。フォーミュラ一覧、スタイルシート、ブックマーク、メタデータ |
| `.4vp` 4D View Pro スプレッドシート | シートの切り替え、保存されたセル値・計算結果、フォント、色、配置、数値書式、罫線、結合セル、行高・列幅。非表示シート・行・列を反映 |
| `.4dm` メソッド・クラスのソース | 行番号、行数、ファイルサイズ付きのシンタックスハイライトされた UTF-8 ソース |
| `.4DForm` フォーム | macOS のフォームレイアウトの近似表示。ページ 0 と選択可能な各ページ、Classic / Liquid Glass のライト・ダーク外観、ローカルのスタイルシート、JSON ポインター、静的な継承フォーム・サブフォーム、XLIFF ラベル |

ヘッダーブロックしか読まないため、220 MB のデータファイルでも約 30 ms でプレビューできます。

保存されたセットのプレビューは、確認済みのリトルエンディアン `70D4` 形式を、
32,768 レコード単位の空ページ・全選択ページやビットマップも含めて、4D なしでデコードします。
レコード番号は 0 始まりのストレージアドレスであり、フィールドの値やセレクション内の位置ではありません。
件数と分布はセット全体を対象とし、解析が完了した場合は最初の 200 個の連続範囲を表示します。
デコーダーはビットマップデータを 256 KiB 単位でストリーム処理し、恣意的なファイルサイズの上限はありません。
既定の解析時間（1.5 秒）を使い切った場合は、部分的なプレビューであることを明示します。
件数は下限値となり、調べていないアドレスは不明のまま、未完了の範囲には印が付きます。
CLI の `--thorough` は時間制限を外しますが、出力の上限は外しません。
旧形式のビッグエンディアンのセットや未知のページエンコーディングは、推測せずにその旨を報告します。
[バイナリ形式の根拠と制限](docs/4ST-FORMAT.md)を参照してください。

クイックレポートへの対応は実験的なもので、4D 18〜21 で確認されたチャンク形式の Unicode フォーマット
（ストリームバージョン 25〜28）を、どちらのバイトオーダーでも扱います。
これはデザインのプレビューであり、実際のレポートや印刷結果ではありません。フィールド参照はテーブル番号と
フィールド番号で表示され、トークン化されたフォーミュラ、レコード、合計マクロ、ピクチャー、
ページ分割、ネイティブのプリンター設定は評価されません。
[バイナリ形式の根拠とフィクスチャの作成手順](docs/QUICK-REPORT-FORMAT.md)を参照してください。
CLI の [`fourdql qr-convert`](docs/CLI.md#convert-quick-report-definitions) は、
ファイルパスまたは標準入出力を使って `.4qr` と編集可能な JSON を相互変換します。
未解釈のフォーミュラ、ピクチャー、プリンター設定も保持します。

ラベルのプレビューは、[4D Labels コンポーネント](https://github.com/4d/4D-Labels)で使われる
ネイティブ XML の `.4lbp` 形式を読みます。JSON や旧形式のバイナリ `.4lb` ファイルは対象外です。
表示されるのは静的なラベルデザインと推定したシートレイアウトで、
フィールド、フォーミュラ、ラベルメソッド、プリンター設定は実行されません。
ラベルがプロジェクトの `Project/Sources` または `Resources` 以下にあり、フォーム名を一意に解決できる場合、
保存されたテーブルフォームは `.4DForm` のレンダラーで描画されます。フォームが見つからない場合や
未対応の図形はプレビューの注意書きとして表示されます。
[形式の意味と制限](docs/LABEL-FORMAT.md)を参照してください。

4D Write Pro のプレビューは、4D が `.4wp` として保存する ZIP 形式の XHTML（ZIP でない XHTML も可）を読み、
4D を使わずに静的なページとして組み立て直します。要素と CSS プロパティはすべて 4D 独自の表記から変換・検証され、
リンクは無効化、リモート画像はダウンロードせず、フォーミュラは評価しません。フォーミュラは参照として表示されますが、
ページ番号、ページ数、セクション名だけは計算されます。ページの区切りは明示的な改ページとセクション区切りのみで、
長い本文が次のページへ流し込まれることはなく、アンカーオブジェクトの周りの文字の回り込みも再現しません。
[形式のメモ](docs/WRITEPRO-FORMAT.md)を参照してください。

独立した [4WP Editor Web アプリ](web-editor/README.md)では、`.4wp` のテキストと書式を
ブラウザーで編集できます。元の構造を保持するインポート・エクスポート、6言語のUI、
ライト・ダーク表示に対応する実験版です。Swift の Quick Look ランタイムとは独立して動作し、
4D 本来のレイアウトやフォーミュラの評価は提供しません。選択範囲の書式変更、リンク、画像、
単純な表・リスト、検索・置換、取り消し・やり直し、ローカルのバージョン管理と再読み込み時の
復旧に対応しています。対応する編集ではネイティブのブックマーク位置を調整し、未対応の範囲や
構造は保護します。ブックマーク管理とフォーミュラ表示は
[#40](https://github.com/miyako/4d-ql/pull/40)・[#41](https://github.com/miyako/4d-ql/pull/41)で、
限定された列の挿入、セルをまたぐブックマーク、結合セル内の文字編集と保護理由の6言語表示は
[#42](https://github.com/miyako/4d-ql/pull/42)で`main`に提供済みです。
書類全体の用紙プリセット・カスタム寸法、向き、余白、
表示単位を設定するページ設定は[#43](https://github.com/miyako/4d-ql/pull/43)でmainにマージされています。
この独立した未マージの変更では、対応範囲内の改ページ・セクション区切り、
セクション名・向き・余白と明示的な継承の設定を追加しています。デプロイはしていません。
段組み・タブと印刷は今後の別ステップです。
ヘッダー・フッター編集、浮動オブジェクト、自動ページ分割は未実装です。
正確な対応範囲、ローカル保存の制限、フル4Dでの互換性検証手順は
エディターのREADMEを参照してください。Pagesのデモは`main`に基づき、未マージの変更は反映しません。
ブックマーク管理は[#40](https://github.com/miyako/4d-ql/pull/40)で`main`に提供済みです。
フォーミュラ表示はネイティブのソースと判別可能な保存値を表示し、
フォーミュラ自体は読み取り専用のまま、ネイティブ検証済みの周辺テキスト編集のみを許可します。
フォーミュラの評価は行いません。
[ロードマップ・対応状況の一覧](web-editor/README.md#roadmap-and-status)では、提供済み、
開発中、承認済みの次のステップ、未承認・未定の将来案を区別しています。

4D View Pro のプレビューは静的な表として描画され、表示時に 4D や SpreadJS を必要としません。
保存された計算結果を表示し、フォーミュラ、4D カスタム関数、リンクは実行しません。
保存された結果がない場合はフォーミュラを参照として表示します。表示は最大 16 枚の可視シート、
各シート 200 可視行・40 可視列に制限され、省略されたセルは注意書きで明示します。
グラフ、画像、条件付き書式、印刷レイアウトは再現しません。
[ネイティブ形式の調査とフィクスチャの作成手順](docs/VIEWPRO-FORMAT.md)を参照してください。

### フォーム描画の共有

このリポジトリは macOS の Quick Look アプリと拡張機能を提供します。独立したフォーム画像用 CLI は
[4d-form](https://github.com/miyako/4d-form) にあり、2 つ目のパーサーや調整済みレンダラーを
持つ代わりに、公開ライブラリの `FourDFileKit` と `FourDRender` を利用しています。暫定的な
HTML/JSON 専用の `fourdform` 実行ファイルは Quick Look のリリース対象ではありません。

`FourDRender.FormRenderer` は、4D、Quick Look、ホストアプリ、その XPC サービスのいずれも使わずに、
プロセス内で HTML とバージョン付き JSON を生成します。
[共有 API と静的機能の仕様](docs/FORM-RENDERER.md)および
[Windows 向け引き継ぎ資料](docs/WINDOWS-HANDOVER.md)を参照してください。ライブラリは
Windows でもビルドでき、フォームは 4D 21 に合わせて調整した Windows Classic と Fluent UI の
ライト・ダーク外観で描画されます。プラットフォームは
`FormRenderer.render(url:preferredLanguages:platform:options:)` で選択します。

macOS の Quick Look のフォームプレビューにも、macOS/Windows の切り替えの奥に Windows の外観が含まれています。
Segoe UI は再配布できないため、インストールされていない環境では Windows のテキストを、
埋め込みの [Selawik](https://github.com/microsoft/Selawik) フォント（Segoe UI とラテン文字の
送り幅が同じ、Microsoft によるオープンソースの代替フォント）で計測・描画します。
グリフの形は異なり、ラテン文字以外のテキストは別のフォントにフォールバックします。

読み込み・書き出し設定のプレビューは、フィールドの順序（フィールド番号とは異なる場合があります）を保持し、
欠けている値は明示的に表示し、未知のフィールド型や追加オプションもそのまま残します。
サマリーカードにはテーブル、選択されたフィールド数、形式、エンコーディングが表示され、その下に
保存された順序（左から右、上から下）でフィールドカードがコンパクトなレスポンシブグリッドに並びます。
順序番号のラベルはありません。元の型記号にはホバー時とアクセシビリティ用のラベルがあり、
未知の型はテキストとして表示されます。名前は切り詰めずに折り返し、31 文字の名前もそのまま表示されます。
二次的な設定とオプションは、その下に枠なしのキーと値の組で表示されます。
XML は 4 MiB、20,000 要素、ネスト 32 階層までに制限されています。
不正な XML やカスタムエンティティは拒否され、外部エンティティは読み込まれません。
XML 宣言の前にある ASCII の空白は許容されます。書式に関する警告はプレビューではなく JSON 出力に残ります。
プレビューに表示されるのはフィールド 500 件、オプション行 500 件までで、省略された件数は明示されます。
JSON 出力には解析した設定がすべて含まれます。

メソッドのプレビューはプロセス内の正規表現レキサーを使用します。4D 本体、tool4d、
LSP サーバー、JavaScript、ネットワークアクセスはいずれも不要です。ハイライト対象は
コメント、属性ヘッダー、文字列、数値、日付・時間リテラル、キーワード、
変数、テーブル・フィールド参照、トークン化されたコマンド（`:C…`）と定数
（`:K…:…`）、呼び出し名です。トークン化されていないコマンドは経験則でハイライトされます。
意味解析や構文チェックではありません。トークンの分類は
[miyako/language-4dm-zed](https://github.com/miyako/language-4dm-zed)
とその [tree-sitter 文法](https://github.com/miyako/tree-sitter-fourd) を参考にしています。
プレビューは最大 256 KiB を読み込み、最大 1,000 行を表示します。切り詰めた場合は
（CLI の `--thorough` モードでも）その旨が表示されます。UTF-8 BOM と
Windows・クラシック Mac の改行コードに対応しています。不正な UTF-8 は報告されます。

フォームのプレビューは、実行中の 4D ではなく自己完結した SVG キャンバスで描画します。
JSON オブジェクトの宣言順（描画順）を保持し、各ページの背後にページ 0 を重ね、保存された座標と
フォームサイズのアンカーに従い、スクロール可能なキャンバスとスクリプトを使わないページ・外観の
切り替えを提供します。
Quick Look では、カタログと同様のカーソル中心のピンチズーム、対数スライダー、+/− ボタン、
100% へのリセット、フォームキャンバス上のドラッグによるパンが加わります。
ズーム範囲は 1%〜800% で、プラットフォーム・外観・ページを切り替えても維持され、切り替えボタンや
メタデータは拡大縮小されません。通常のスクロールも使え、キャンバス内では Control キーを押しながら
スクロールしてもズームできます。単体の HTML はスクリプトを含まず、10%〜200% のズームプリセットを備えます。
テキストは個々の文字幅を合計するのではなく、CoreText のシェーピングと単語境界での改行を使います。
合成文字、明示的な空行、フォントの特性は保持され、テキストは保存された範囲でクリップされます。
計測と WebKit の SVG 出力では同じ書体が一貫して選ばれます。
最初は閲覧者の外観が使われ、フォームで `colorScheme` が明示されていればそれに従います。
Liquid Glass のボタンとドロップダウンは、ドキュメントに記載された 27 ポイントの角丸コントロールの
しきい値と、計測したネイティブの高さ・フォントのバリエーションを使います。
背の高いドロップダウンは矩形の表示にフォールバックします。Classic には独自の自動フォントのしきい値、
既定のトグルの高さ、アクセントカラーのドロップダウン矢印領域があります。
Classic と Liquid Glass のタブはコンパクトな中央揃えのセグメントで、ネイティブエディターの
テンプレートの初期選択を使います。これは実行時に計算される値ではありません。
自動のグループタイトルは計測した 10 ポイントのフォント、メインフォントテーマは
13 ポイントの太字を使い、明示的なフォントサイズとウェイトが優先されます。
グループの枠はタイトル帯を確保し、枠全体でキャプションの位置を揃え、
タイトルのないグループにキャプションを作り出すことはありません。保存されたテキスト・入力の余白と、
明示的な上・中央・下揃えはテキストのビューポート内で適用されます。
自動配置ではネイティブ風の既定値が保たれます。これらのテキスト・入力のプロパティは
21 R5 で導入されたため、それより古いネイティブの参照では検証できません。
ワードラップを無効にすると、明示的な改行は保持したまま、長い行は水平方向にクリップされます。
リストボックスのヘッダーにはネイティブ風の個別のリサイズグリップがあり、
フッターはヘッダーではなく入力の背景を使います。
角丸のテキスト枠は保存されたテキスト範囲の外側に広がり、1 行の入力の角丸は
コントロールの高さで上限が決まります。入力テキストは保存された余白の位置から始まり、
余分な内側の余白は加えません。キャプションとアイコンのレイアウトは
`textPlacement` と `imageHugsTitle` に従い、既定ではアイコンがタイトルの上に来る計測済みのレイアウトです。
両端揃えで折り返された段落は単語間のスペースを広げますが、最終行は広げません。

スタイルシートは 4D と同じ順序で読み込まれます: `Project/Sources/styleSheets.css`、
`styleSheets_mac.css`、そしてフォームの `css` 参照（Windows 専用の参照は無視されます。
Windows での描画では代わりに `styleSheets_windows.css` と Windows 専用の参照を使います）。
対応するセレクターは、オブジェクトタイプ、名前、クラス、複合、ユニバーサル、属性セレクターです。
入れ子の `prefers-color-scheme` / `form-theme` メディアクエリは外観ごとに評価されます。
JSON のプロパティは通常の CSS より優先されますが、`!important` はそれを上書きできます。
よく使われる Web のプロパティ名は 4D の名前に対応付けられ、リストボックスの列、ヘッダー、
フッターのスタイルにも適用されます。未対応のセレクター、@ ルール、利用できない依存ファイルは
プレビューの注意書きとして表示されます。
1 回の解析の中では、スタイルシートは正規化された依存パスごとに一度だけ解析され、静的コンテキスト間で
再利用されます。繰り返し参照されてもカスケードの順序は保たれます。

再帰的な `$ref` ポインターは、ローカルと外部の JSON ドキュメント、RFC 6901 のエスケープ、配列の
インデックス、ローカルプロパティによる上書きに対応しています。相対パスは参照元ドキュメントを基準に
解決されます。ローカルのピクチャー、ボタンのアイコン、その `_dark` 版は埋め込まれ、
ピクチャーボタン・ポップアップのスプライトシートは最初のフレームを表示します。ラスター画像は
サイズに上限のある PNG に変換されます。基本的な受動的 SVG 画像に対応していますが、アクティブな内容、
外部参照、未対応の SVG 構文は拒否されます。
表示形式が省略された静的ピクチャーは、固有のサイズを保ったまま、コンテナでクリップされる前に
オブジェクトの矩形全体の中央に配置されます。拡大縮小・比例などの形式が明示されていれば、
保存された動作に従います。
依存ファイルは、通常のプロジェクトであればそのパッケージフォルダ内、単体のファイルであれば
選択したフォームのフォルダ内に限定され、シンボリックリンクを解決した後もこれは変わりません。
`/PROJECT`、`/SOURCES`、`/RESOURCES`、`/PACKAGE` はプロジェクトが見つかった場合にのみ対応付けられます。
実行時の `/DATA` と `/LOGS` のパス、ネットワークパス、変数のピクチャーは読み込まれません。
静的な継承フォームは、受け取る側のフォームのプロパティを置き換えることなく、背景と最初のページの
オブジェクトをローカルのオブジェクトの背後に加えます。
静的に名前が指定されたプロジェクトのサブフォームは、背景と最初のページをコンテナ基準の座標で表示し、
コンテナでクリップされます。各ソースはそれぞれの CSS、ポインター、ピクチャー、ローカライズの
コンテキストを保持します。循環参照、動的な参照、利用できないフォームは、注意書きやプレースホルダーとして
表示されます。
インラインのオブジェクト値によるフォーム参照は、正規のスキーマではない旨の注意書きを付けて近似表示します。
動的な 4D コマンドはオブジェクトによる記述を受け付けますが、保存されたフォームのスキーマでは参照は文字列であり、
ネイティブの名前付きキャプチャではプレースホルダーが描画される場合があります。
プロジェクトの XLIFF ラベルは、名前、番号、オブジェクト名による参照を、優先言語の詳細度と
ドキュメントに記載されたフォールバックフォルダに従って解決します。曖昧な翻訳や欠けている翻訳は、
参照のまま注意書き付きで表示されます。ローカライズ用のメソッドは実行されません。

**Finder の Quick Look サンドボックスは、既定では選択したファイルにしかアクセスを許可しません。**
CLI は同じ解析を使いますが、通常はプロジェクトのリソースも読み込めます。
利用できないリソースや未対応の機能はキャンバスの上に警告として表示され、
個々の説明は「Preview notices」に表示されます。

ネイティブのコントロールは近似表示であり、AppKit のウィジェットとピクセル単位で同一ではありません。
バインドされた入力、ドロップダウン、コンボ、動的なタブは、実行時の値を作り出す代わりに保存された式を表示します。
静的なタブのラベルとリストボックスのヘッダーは表示され、リストボックスの本体にはレコードではなく
式のプレースホルダーが表示されます。動的または利用できないサブフォーム、Web エリア、4D Write Pro、
4D View Pro、プラグインはプレースホルダーのままです。メソッド、動的なスタイル設定、アプリケーションレベルの
外観設定は実行・解決されません。ネイティブのアニメーション、フォーカスリング、Liquid Glass の
マテリアルは再現されません。

### Finder でのプロジェクトリソースへのアクセス許可

macOS 13 以降のチーム署名済みビルドでは、ホストアプリのウェルカムウインドウに
**Choose Desktop...**、**Choose Documents...**、**Choose Downloads...** のショートカットがあります。
それぞれフォルダ選択パネルを開き、フォルダを確定するとその下にあるすべてのプロジェクトに
読み取り専用のアクセスが許可されます。**Choose another folder...** では、他のプロジェクトフォルダ、
または `Project` と `Resources` を含む個別のパッケージフォルダ（`Project` サブフォルダではありません）を
許可できます。
読み取り専用のフォルダブックマークを保持するのはサンドボックス化されたサービスだけです。
Quick Look 拡張機能がファイルシステムの例外を受け取ったり 4D を実行したりすることはありません。
許可はアプリを閉じた後も保持されます。パスを追加するには **4D Quick Look** を再度起動してください。
Quick Look のプレビューウインドウからはフォルダの許可はできません。
**Remove folder authorizations...** は保存されたフォルダの許可をすべて取り消します。

許可されたプレビューは、アプリ専用のチーム所有の共有コンテナを使います。
Finder の各リクエストに対して、埋め込みの XPC サービスが現在のフォームとその範囲内の依存ファイル、
またはカタログと同じフォルダにあるエディターのレイアウトを解析し、自己完結した HTML を IPC で返します。
拡張機能が共有コンテナに書き込んだり、ホストアプリを起動したりすることはありません。
リクエストと応答は、毎回新しいノンス、選択したファイルの内容のハッシュ、レンダラーのビルドに結び付けられます。
フォームのソースは 4 MiB、カタログのソースは 32 MiB の上限がそのまま適用されます。ヘルパーがない場合、
許可の失敗、ソースの変更、タイムアウトの場合は、注意書きを表示して選択したファイルのみのプレビューを
表示し、古いプロジェクトプレビューを黙って表示することはありません。
役割ごとの XPC セッションは、受け入れる前に署名 ID を確認します。
プロジェクトの許可と取り消しができるのはホストアプリだけです。プレビューの役割は読み取り専用です。
各サービスは 2 つのリスナーを再利用し、処理を 32 件までに制限し、HTML の応答を 32 MiB までに制限します。
クライアントには、選択したソースのハッシュ計算と 2 回の XPC 呼び出しを含めて 4 秒の期限があります。

実際の Finder での確認により、ホストアプリを閉じた後の許可の保持、サービスの自動起動、
静的なフォーム合成と XLIFF、許可の取り消しが検証されています。
CSS、外部の JSON テンプレート、SVG を変更すると、選択したフォームのチェックサムが変わらなくても
次の Finder プレビューに反映されました。

この機能のために、フルディスクアクセスや他のアプリのデータへの広範なアクセスを許可しないでください。
アドホックビルドではプロジェクトの共有は無効のままですが、選択したファイルのプレビューと
開発用の `fourdql` CLI は使えます。署名済みの macOS ビルドでは、既定で署名チームの
`<Team ID>.<bundle ID>.ProjectContext` App Group を使います。独自の
`PROJECT_GROUP` は署名設定で許可されている必要があります。

描画の参考資料は、正規の
[4D フォーム](https://github.com/miyako/skills/tree/dist/skills/4dform)、
[CSS](https://github.com/miyako/skills/tree/dist/skills/4dcss)、
[CLI](https://github.com/miyako/skills/tree/dist/skills/4dcli) の各スキルと、
macOS 26.7 上の 4D 20.8 build 101985、21.2 LTS build 100653、
21 R4 build 100208、21 R5 build 100156 でのキャプチャを組み合わせたものです。名前を指定した
[`FORM SCREENSHOT`](https://developer.4d.com/docs/commands/form-screenshot)
のキャプチャは CSS を無視します。ロード済みフォームのスクリーンショットや印刷されたフォームでは
CSS が適用されることがありますが、どちらも実際のダイアログの代わりにはなりません。計測した
Liquid Glass のライトの寸法は、プレビューの段階的なサイズ、リストボックスの式の 1 行、
ページ 0 の重ね方、1 行の入力の非対称な角丸に反映されています。LTS のフルアプリケーションと
LTS の tool4d からは Classic のライト・ダークの寸法とカラーパレットを、R4/R5 のフル `4D.app` からは
Liquid Glass のライト・ダークのエディターテンプレートのキャプチャを取得しました。
それらのテンプレートのパレットがプレビューに反映されています。
4 つのフルアプリケーションすべてで、正規の `DIALOG` / `CALL FORM` の流れと、`onTimer` フォームメソッドを
持つブロッキングの `DIALOG` の両方を使って、両方の配色で実際のダイアログもキャプチャしました。
実行時の入力の外観とキャンバスの透明な領域は、名前を指定したフォームの出力とは異なります。

初期のクラッシュやタイムアウトからは結論が得られませんでした。再起動後、逐次的な再試行で
デコード可能なスクリーンショット、空白でない PDF、正常終了が得られました。
[`FORM EDIT`](https://developer.4d.com/docs/commands/form-edit) は 4 つのフルアプリケーションすべてで
エディターウインドウを開き、ウインドウのスクリーンショットを証拠として保存しています。
検証用のセットアップでは、旧形式のコンポーネント読み込みダイアログを防ぐため、4D を起動する前に
`{"dependencies":{}}` を含む `Project/Sources/dependencies.json` を作成する必要があります。
この事前手順を省いたことで、21.2 の GUI での最初の再試行はブロックされました。
このファイルを追加するだけで、元の互換性バージョンのプロジェクトは完了しました。
中断された実行からは、エンジンの能力について結論を導いていません。

再試行した R4/R5 の tool4d での検証では、SVG のデコードで寸法が 0 になり、
名前を指定したフォームのダーク出力は一部がライトのままでした。フル GUI のキャプチャでは
同じ SVG とダークのコントロールが描画されました。これらの観察結果は、検証したビルド、入力、
キャプチャ方法に固有のものです。4 つのプレビュー外観はいずれも近似表示であり、
ネイティブの描画とピクセル単位で同一ではありません。

フォームの JSON は 4 MiB、ネスト 64 階層、値 100,000 個までに制限されています。
描画順が曖昧にならないよう、重複したキーは拒否されます。依存ファイルは通常ファイル 64 個、
各 4 MiB、合計 16 MiB までに制限されています。ポインターと静的フォームの展開は値 100,000 個、
深さ 64 までです。埋め込まれたオブジェクトは外観ごと 1,000 オブジェクトの上限を共有します。
XLIFF の解析は XML ノード 20,000 個、深さ 64、テキスト 1 MiB までに制限され、外部エンティティは
無効です。CSS はファイルごとにルール 5,000 個、宣言 20,000 個、入れ子のメディアブロック 16 個、
オブジェクトとルールの照合 1,000,000 回までに制限されています。描画されるのはページ 16 枚まで、
外観ごとに 1,000 オブジェクトまで、リストボックスの列 64 個まで、グリッドの行 200 行までで、
キャンバスは 1 辺 8,192 ポイントで切り取られます。画像は 32 メガピクセルまで、ラスターの
サムネイルは 2,048 ピクセルまでで、埋め込み画像の合計は 24 MiB までです。
テキストのシェーピングはラベルごとに UTF-16 で 4,096 単位、100 行までで、
入力の境界で合成文字が分割されることはありません。
元の JSON は解析出力に保持され、折りたたみ部分には 256 Ki 文字まで表示されます。
解析は 4D のスキーマの完全な検証ではありません。

### フォームの視覚的ベンチマーク

`Tests/FourDFileKitTests/Fixtures/FormBenchmarkProject` には、自作のフォームが 4 つ含まれています:
Typography、Controls、ContactInvoice、References。それぞれ 2 ページを 4 つの外観で描画して
32 ケースとなり、文字組み、コントロール、リストボックスのヘッダー・フッター、プロジェクト参照について
オブジェクトごとの切り抜きを作成します。外部アプリケーションのフォームソースは含まれていません。

```sh
python3 scripts/form-benchmark.py --validate-only
caffeinate -di python3 scripts/form-benchmark.py --output /absolute/artifacts/form-benchmark
python3 scripts/form-benchmark.py --output /absolute/artifacts/form-benchmark \
  --fourdql build/fourdql --compare-only
```

macOS のハーネスは、4D のフルアプリケーションを逐次的に使い、インストールされたフォームの
スキーマとバリデーター、WebKit のスナップショットヘルパー、Pillow を使用します。エンジンを起動する前に、
依存マニフェストを含む書き込み可能な専用のプロジェクトを作成します。
compatibilityVersion を 2100 に正規化するのはそのコピーだけです。コミットされたフォームと
プロジェクト参照は変更されません。`--compare-only` は検証済みのネイティブキャプチャを再利用し、
4D を起動することはありません。エンジンのパス、フォーム、テーマは `--help` に表示される
オプションで選択できます。

`gallery.html` と `metrics.json` には、ネイティブとプレビューの比較、前景の範囲、
マスクの重なり、RGB の誤差が含まれます。32 ケースがすべて完了しても、それはキャプチャの網羅を意味し、
ピクセルの同等性や視覚的なスコアの合格を意味するものではありません。
名前を指定したスクリーンショットは CSS を無視します。既知の CSS・ポインターのキャプチャコンテキストの
差異は表示されたままですが、比較可能なランキングからは除外されます。ロード済みフォームの
フォント取得と実際の Finder での確認はそれぞれ別の証拠であり、互いに置き換えられる
スクリーンショット方式ではありません。GUI の確認中はデスクトップをロックしないでください。
`caffeinate -di` は、設定を変更したり手動・ポリシーによるロックを無効にしたりすることなく、
コマンドの実行中だけディスプレイとシステムのアイドルスリープを防ぎます。

実際の HDI による調整では、さらに
`4d-depot/HDI_Buttons`、`HDI_RoundedCorner`、
`HDI_FormObj_VericalAlignAndPadding` の固定リビジョンも対象にしています。外部のコーパスは
指定した成果物ディレクトリにのみダウンロードされ、このリポジトリには取り込まれません。ネイティブの
コピーからは上流のメソッドとコンポーネントを除外し、独自のキャプチャメソッドだけを使います。
名前を指定した 24 ケース、別途用意した安全なロード済み CSS の 1 ケース、R5 の余白検証用の 6 ケースで、
保存されたプロパティと実行時のみの変更を区別します。LTS のキャプチャでは R5 のテキスト・入力の
配置を検証できないため、それらの領域は実際のエンジンバージョンに応じて除外されます。
オフスクリーンでロードしたときの配置は、実際のダイアログの配置とはみなしません。
Arial で計測した 13/15 ポイントでの 15/17 ポイントの行送りは、他のフォントの寸法には適用しません。

```sh
caffeinate -di python3 scripts/form-hdi-benchmark.py --output /absolute/artifacts/hdi
python3 scripts/form-hdi-benchmark.py --output /absolute/artifacts/hdi \

caffeinate -di python3 scripts/form-padding-probe.py \
```

### 表示されるもの、されないもの

保存されたクエリのプレビューは、バージョン 3 の UTF-8 JSON（BOM 付きを含む）を
4 MiB まで解析します。条件カードは最大 200 件まで表示されます。元の JSON と CLI の
JSON 出力には、未知の入力を含むすべての行とプロパティが残ります。
単独の `.4df` ファイルにはテーブル名・フィールド名や型が含まれていません。
そのため、型に依存する条件コードはフィールド型を推測せずに候補を並べて表示し、
未知のコードは保存された番号のまま表示します。
値は保存されたとおりに表示され、4D のフォーミュラとして実行・解釈されることはありません。
「Original JSON」の折りたたみ部分に添えられるのはバージョン番号だけです。その他の
メタデータは説明的な脚注ではなく JSON の中で確認できます。
他のバージョンの場合は注意書きと元の JSON を表示し、旧形式のバイナリクエリや
不正な JSON はエラーとして報告されます。

Quick Look の表示領域は限られているため、サマリーチャートはコンパクトに保たれます。テーブルが
500 あるデータファイルでも 5 つしかないファイルでも、サマリーが占める領域は同じです
（詳細はバーにマウスを重ねると表示されます）。
一方、カタログの図はすべてのテーブルが入るようにスクロール可能なキャンバスを広げます。

`.4DB` と `.4DD` のフィールド型チャートは、カタログ本来のインライン SVG アイコンと、
それに合わせたライト・ダークの色を使います。8 つの分類ごとの件数は変わりません。
テキスト・UUID は存在する型ごとに異なるアイコンを表示し、日付・時間は時間のみのチャートも含めて
カレンダーのアイコン 1 つを使います。未知の型は中立的な疑問符のアイコンと「Other」の件数のままです。

カタログのプレビューは図を先頭に表示し、サマリーチャートやリレーション一覧は表示しません。
メタデータは折りたたまれた **Catalog details** の中で確認できます。
カタログの図はスクリプトやネットワークリクエストを含まない自己完結した SVG です。
可能であればストラクチャエディターに保存された位置を再利用し、それ以外の場合は
テーブル数に応じて大きくなる決定的なグリッドにフォールバックします。位置は `.4DCatalog` の XML に
埋め込まれているか、同じフォルダにある `catalog_editor.json` の tables オブジェクトにテーブル名ごとに
保存されています。有効な外部座標が優先され、欠けている・無効なエントリは埋め込みの位置のままです。
数値の座標と 4D の文字列値の座標の両方に対応しています。読み取れない、不正な、大きすぎる
エディターファイルは、カタログを隠すのではなくパーサーのメモとして報告されます。
エディターファイルは 4 MiB、深さ 64、JSON の値 100,000 個までに制限され、通常ファイルである必要があり、
シンボリックリンクを通じてカタログのフォルダの外を指すことはできません。
Finder では、プレビューサービスがこのファイルを読めるよう、ホストアプリで親のプロジェクトフォルダを
許可してください。アクセスできない場合でも、埋め込みのレイアウトや自動グリッドは使えます。
Finder ではビューベースの Quick Look 拡張機能が専用の `WKWebView` を使います。
Web ビュー自体をリモートコントローラーのルートにはせず、反転していない AppKit の
ルートビュー内でサイズを調整します。ネイティブの拡大イベントを直接処理するため、
Finder がキャッシュ済みプレビューに戻ったときも、ローカルのジェスチャ認識器が
駆動されることにピンチ操作を依存させません。
図の上でピンチするとカーソルを中心に連続的にズームでき、対数スライダーや +/- ボタンも使え、
100% を選ぶとリセットされます。ズーム範囲は 1%〜800% で、拡大縮小されるのは SVG とその
スクロール範囲だけで、周囲のプレビューは変わりません。
2 本指のスクロールで図をパンでき、キャンバスのドラッグでもパンできます。
コントロールはキーボード操作に対応しています。図の外での拡大操作ではページはズームしません。

ビューアーは独自の操作用コードを、分離された WebKit のコンテンツワールドに組み込みます。
ドキュメント側の JavaScript は無効で、外部へのナビゲーションやリソースの読み込みはブロックされ、
プロジェクトフォルダのベース URL やネイティブのスクリプトブリッジは公開されません。
サンドボックス化されたプレビュー拡張機能は、プレビューの内容がリモートのリソースを読み込めないにもかかわらず、
WebKit のサブプロセスとの通信のためにネットワーククライアントのエンタイトルメントを必要とします。
ホストとプロジェクトサービスにはこのエンタイトルメントは与えられていません。
CLI の HTML は、移植可能な代替手段としてスクリプトを含まず、10%〜200% のズームプリセットを備えます。
図の中はスクロールでき、名前や接続線にマウスを重ねると詳細が表示されます。テーブル名は中央揃えです。
図をすっきり保つため、リレーション名は接続線のツールチップにのみ表示されます。
主キーのフィールド名には下線、インデックス付きフィールド名は太字、
非表示の名前は斜体で表示されます。複数のフラグがある場合はこれらのスタイルが組み合わされます。
カードは 21 ポイントのコンパクトなフィールド行と本来のインライン SVG の型アイコンを使い、
完全な型名と文字の長さはホバー時の詳細に表示されます。カードの幅は表示される名前から計測されるため、
有効な 31 文字の名前は、幅の広い文字やラテン文字以外のテキストも含めて完全に表示され、
すべてのカードを同じ幅に揃えることはありません。4D 独自の画像素材は同梱していません。
プレビューは、保存された 12,000 ポイントを超えるレイアウトも含め、全体のレイアウトに合わせた
キャンバス上にすべてのテーブルと解決できたすべてのリレーションを表示します。カードにはテーブルごとに
フィールドが 8 件まで表示されます（主キーと結合に使われるフィールドを優先）。テーブルごとの
フィールドの省略はカード上に表示されます。省略の合計と凡例は、図の上ではなく
図のツールチップ・アクセシビリティ説明に含まれます。
JSON 出力には解析したテーブル、フィールド、リレーションがすべて含まれます。XML カタログは
32 MiB、200,000 要素、ネスト 128 階層までに制限されています。不正な XML や
カスタムエンティティ宣言は拒否されます。4D 標準の外部 DOCTYPE は、
DTD を読み込まずに受け付けます。

* **表示されるもの:** 中身（テーブル、レコード、フィールド）、ファイルが期待どおりに開き
  動作するかを左右する情報（データベース UUID、言語、`@` ワイルドカード規則、
  インデックスエンジンのマーカー、ジャーナル、暗号化）、そして若干の参考情報
  （フォーマットのバージョン、ストレージ、バイトオーダー）。
* **日本語の照合オプション**（ICU、二次・四次の比較強度、ひらがな優先など）は、
  それが適用される唯一のケースである「ICU を使わない日本語」の場合にのみ表示されます。
* **表示されないもの:** エンジン内部の情報（ブロックサイズ、フラッシュやヘッダーのカウンター、
  LCID、シーケンス数、フィールドごとの一覧）。これらは `fourdql --json` で確認できます。

## 構成

```
Sources/
  FourDFileKit/          analyzer layer: bytes -> typed Codable model (no UI)
    Core/                ByteSource (pread), BinaryReader (bounds-checked),
                         FileAnalyzer protocol, AnalyzerRegistry
    DB4D/                the shared .4DD/.4DB container format
    Catalog/             .4DCatalog XML definitions and relation references
    Text/                XML .4DSettings / .4DLink / .4DPreferences and JSON .4DProject source text,
                         structured .4si import/export settings
    Query/               JSON .4df saved query conditions and metadata
    Set/                 binary .4st membership, compressed pages and bounded ranges
    QuickReport/         bounded, endian-aware binary .4qr report templates
    Method/              bounded UTF-8 .4dm reader and regex lexer
    Form/                ordered JSON, bounded pointers/dependencies,
                         macOS stylesheet cascade, static forms and XLIFF
  FourDRender/           rendering layer: model -> Report -> HTML
    Report.swift         generic page model (stats, badges, tables, bars, disclosures)
    *Presenter.swift     one presenter per model kind
    HTMLRenderer.swift   the only place that knows about HTML/CSS
    PreviewPipeline.swift
  FourDQuickLookExtension/  view-based QLPreviewingController with project authorization
  FourDQuickLookUI/       owned WKWebView and isolated canvas zoom/pan controls
  FourDProjectAccess/    read-only authorization and bounded shared-preview exchange
  FourDQuickLookHost/    hosting app and sandboxed project-preview helper
  fourdql/               CLI using the same pipeline
Support/                 Info.plist templates, entitlements
scripts/build.sh         builds and signs "4D Quick Look.app"
```

各レイヤーが接するのは次の 2 か所だけです。

* **アナライザー → プレゼンター**: `kind` 文字列（例: `db4d.data`）を持つ `AnalysisModel`。
* **プレゼンター → レンダラー**: `Report`。

つまり、表示を改善するには `HTMLRenderer`（すべてのファイルに効く）または
プレゼンター（1 つのファイル系統に効く）を編集すればよく、パーサーの修正がこれらに及ぶことはありません。

## ファイル形式の追加

1. `FourDFileKit` に、独自の `AnalysisModel` を返す `FileAnalyzer` を書きます。
   扱う UTI を列挙します（4D.app は多数の UTI を宣言しています: `com.4d.4d.catalog`、
   `com.4d.4d.method`、`com.4d.4d.form`、`com.4d.4d.journalFile`、
   `com.4d.4d.index-data` など）。
2. それを `AnalyzerRegistry.default` に登録します。
3. `FourDRender` に `ReportPresenter` を書き、`PresenterRegistry.default` に登録します。

拡張機能の Info.plist の `QLSupportedContentTypes` はビルド時にレジストリから
生成される（`fourdql --content-types`）ため、手動で同期させる一覧はありません。

## インストール

[Releases](https://github.com/miyako/4d-ql/releases) から `.dmg` をダウンロードし、
**4D Quick Look** をアプリケーションフォルダにドラッグして、macOS がプレビュー拡張機能を
登録するように一度起動してください。アプリは Developer ID で署名され、公証済みです。
Finder に古いプレビューが表示される場合は `qlmanage -r` を実行してください。

Finder の選択を切り替えた後にズームやボタンが反応しなくなる場合は、
実際に使われている拡張機能を確認してください。現在のソースは、リモートの
プレビューウインドウがキーウインドウでなくても最初のクリックを受け付けますが、
別のバンドル ID の古い開発版が更新済みアプリより優先されることがあります。

```sh
pluginkit -m -v -p com.apple.quicklook.preview | grep FourDQuickLook
pgrep -x FourDQuickLookExtension | xargs -I{} ps -p {} -o pid=,command=
```

2 番目のコマンドは、開いているプレビューを処理する実行ファイルを表示します。
意図したアプリのパスと比較し、古い開発版の**正確な**バンドル ID を
`pluginkit -e ignore -i <stale-extension-id>` で無効にしてください。
その後、Quick Look を閉じて `qlmanage -r` を実行し、開き直します。
使用したい拡張機能は無効にしないでください。開発版を無効にしても
`/Applications` の古いアプリは更新されないため、最新リリースもインストールしてください。
`scripts/build.sh --register` は
同じバンドル ID のコピーを置き換えますが、異なる ID の開発版は無効にしません。

### コマンドラインツール

対応形式、インストール、オプション、自動処理時の動作、各形式のスクリーンショットは
[CLI リファレンス（英語）](docs/CLI.md)を参照してください。

別途配布される `fourdql-X.Y.Z-macos-universal.dmg` と `.zip` には、Developer ID で署名・公証済みの
Apple Silicon / Intel 両対応 CLI が含まれます（macOS 12 以降）。
DMG をマウントまたは ZIP を展開して `./fourdql` を実行するか、実行ファイルを `PATH` 内のディレクトリに配置してください。
Quick Look アプリ、4D、Swift のインストールは不要です。

```sh
./fourdql document.4vp
./fourdql --json document.4vp
./fourdql --html document.4vp > preview.html
```

どちらにもプロジェクトと埋め込みフォントのライセンスが含まれます。
DMG には公証チケットをステープルするため、オフラインで配布できます。
単体の実行ファイルと ZIP にはステープルできないため、ZIP 版では
初回起動時に Gatekeeper がインターネット接続を必要とする場合があります。

ホスト型 CI では、ランタイムライブラリを同梱した x86-64 Windows 用 ZIP と Linux 用 tar.gz も
ビルドし、タグからのリリースでは macOS 版と一緒に公開します。Windows 版は未署名です。
Linux 版は Ubuntu 24.04 互換環境向けで、フォームや図の描画は実験的な対応です。
展開したフォルダ全体を保持してください。
[インストール](docs/CLI.md#windows-and-linux-downloads)と
[ホスト型ビルド・リリース](docs/CLI.md#hosted-builds-and-releases)の説明も参照してください。

### アップグレード

Quick Look は登録されている拡張機能のうち見つかったものを使うため、新しいものをインストールした後も
古いコピーがプレビューを提供し続けることがあります。アップグレードするには:

1. `/Applications` のアプリを置き換え、他の場所（ダウンロードフォルダなど）にあるコピーを削除し、
   マウントした DMG を取り出します。
2. 新しいアプリを一度起動します。
3. 古いプレビュープロセスを再起動し、Quick Look をリセットします（またはログアウトして再ログインします）:

   ```sh
   pkill -f FourDQuickLookExtension; pkill -f FourDProjectPreviewService
   qlmanage -r; qlmanage -r cache
   ```

4. 最新のコピーが 1 つだけ登録されていることを確認します:

   ```sh
   pluginkit -mAvvv -i com.github.miyako.FourDQuickLook.Preview
   ```

   古いエントリを削除するには `pluginkit -r "<path to>/4D Preview.appex"` を実行し、
   そのコピーを削除してください。

## ソースからのビルド

```bash
scripts/build.sh --register
```

ユニバーサル（arm64 + x86_64）のリリースビルドを作成し、アドホック署名して、
Launch Services と Quick Look に登録します。常用するには
`build/4D Quick Look.app` を `/Applications` にコピーして一度起動してください。
Finder に古いプレビューが表示される場合は `qlmanage -r` を実行してください。`build/` のコピーは
リリース版をインストールした後も登録されたままで、Quick Look がそちらを使い続けることがあります。
[アップグレード](#アップグレード)の手順に従って登録を解除してください。

ローカルで Developer ID 署名するには次のようにします（Hardened Runtime と
セキュアタイムスタンプは自動的に付与されます）。

```bash
SIGN_IDENTITY="Developer ID Application: …" scripts/build.sh
```

チーム署名を行うと、サンドボックスを変更したり 4D を必要としたりすることなく、プロジェクトフォルダの
許可が有効になります。ビルドは署名 ID から macOS の App Group のプレフィックスを導きます。
`PROJECT_GROUP` は、別の許可されたグループを使う場合にのみ設定してください。

## リリース

リリースは GitHub がホストする macOS ランナーでビルドされます。

* `.github/workflows/ci.yml` は、プッシュとプルリクエストのたびにテストとアドホックビルドを実行します。
* `.github/workflows/bump-version.yml` は、**Actions > Bump version > Run workflow** で
  **patch**（既定）、**minor**、**major** を選べます。最も大きい `vX.Y.Z` タグを繰り上げ
  （minor・major の場合は下位の番号を 0 に戻します）、選択したブランチのチェックアウトしたコミットに
  タグを付けて **Build & Release** を開始します。ソースのバージョン欄を編集する必要はありません。
  CLI からは:

  ```bash
  gh workflow run bump-version.yml -f mode=patch
  ```

  バージョンタグが競合しないよう、バンプは逐次的に実行されます。タグはプッシュされたのに
  リリースの開始に失敗した場合は、再度バンプせずにそのタグに対して `release.yml` を再実行してください。
* `.github/workflows/release.yml` は `vX.Y.Z` タグで実行されます。テストを行い、
  タグのバージョンでビルドし、Developer ID で署名、アプリを公証してステープルし、
  `4D-QuickLook-X.Y.Z.dmg` と `.zip`、および別途署名・公証した
  `fourdql-X.Y.Z-macos-universal.zip` とステープル済みの CLI 用 `.dmg` を公開します。
  ホスト型ランナーで `fourdql-X.Y.Z-windows-x86_64.zip` と
  `fourdql-X.Y.Z-linux-x86_64.tar.gz` もビルドして添付します。リリースするには:

  ```bash
  git tag v0.2.0 && git push origin v0.2.0
  ```

  既存のタグを再ビルドするには: `gh workflow run release.yml -f tag=v0.2.0`
  アプリを再ビルド・置き換えせずに CLI アセットだけを追加・更新するには:
  `gh workflow run release.yml -f tag=v0.2.0 -f cli_only=true`
  CLI のみの公開では、対象の GitHub Release がすでに存在している必要があります。
  macOS の署名資格情報を使わずに Windows/Linux 版だけを公開するには:
  `gh workflow run release.yml -f tag=vX.Y.Z -f portable_only=true`
  対象のタグには移植版のワークフローとパッケージスクリプトが必要です。
  古いソースタグに移植対応を追加するものではありません。

GitHub の組み込みトークンでプッシュしたタグは他のワークフローを起動しないため、バンプのワークフローは
リリースを明示的にディスパッチします。必要な権限は `contents: write` と `actions: write` で、
追加のトークンシークレットは不要です。

macOS のリリースジョブにはリポジトリシークレットが 6 つ必要です: `APPLE_DEVELOPER_ID_CERTIFICATE`
（base64 化した .p12）、`APPLE_DEVELOPER_ID_CERTIFICATE_PASSWORD`、`KEYCHAIN_PASSWORD`、
`NOTARYTOOL_APPLE_ID`、`NOTARYTOOL_TEAM_ID`、`NOTARYTOOL_PASSWORD`。

## 開発

```bash
swift build && .build/debug/fourdql file.4DD            # テキストのサマリー
.build/debug/fourdql --json file.4DD                    # アナライザーの出力
.build/debug/fourdql --html file.4DD > preview.html     # Quick Look の表示そのもの
.build/debug/fourdql --html catalog.4DCatalog > catalog.html
FOURD_SAMPLES=/path/to/samples swift test               # すべてのサンプルをパイプラインに通す
scripts/make-fixtures.sh                                # テストフィクスチャの再生成（tool4d が必要）
bash scripts/make-set-fixtures.sh                       # 検証用の保存セットの再生成（tool4d 21 R5）
bash scripts/make-writepro-fixtures.sh                  # .4wp フィクスチャの再生成（4D 本体が必要。tool4d には Write Pro がない）
bash scripts/make-viewpro-fixtures.sh                   # .4vp フィクスチャと XLSX 参照の再生成（4D 本体と View Pro が必要）
```

`Tests/FourDFileKitTests/Fixtures` のテストフィクスチャ（暗号化可能テーブルを持つデータファイルの、
`Encrypt data file` 実行前と実行後）は、`Tests/Fixtures/encfixture` の小さなプロジェクトから
`scripts/make-fixtures.sh` で作成されます。

インストールした開発版の拡張機能を実際の Finder で試すには:

```bash
scripts/build.sh --register
swiftc scripts/finder-form-preview.swift -o build/finder-form-preview
caffeinate -di build/finder-form-preview /path/to/form.4DForm /path/to/finder-preview.png
# 空白でないスクリーンショットだけでなく、レンダラー固有の表示内容を必須にする:
caffeinate -di build/finder-form-preview /path/to/catalog.4DCatalog /path/to/catalog.png "STRUCTURE DIAGRAM"
```

ハーネスは指定したファイルを選択し、Finder の「ファイル」メニューから Quick Look を開き、
選択が変わっていないことを確認してから、前面にある Finder のプレビューウインドウだけをキャプチャします。
再利用される名前のないプレビューウインドウにも対応しています。ホストアプリには、
Finder と System Events へのオートメーション、UI 操作のためのアクセシビリティ、
スクリーンショットのための画面収録の許可が必要です。ロックされたデスクトップや透明な OS の
キャプチャは明示的に拒否されます。
省略可能な 3 番目の引数を指定すると、そのテキストがスクリーンショットの OCR 結果に含まれることを必須にし、
既知のビューアーのエラーメッセージを拒否します。Finder の汎用ファイル表示で通ってしまわないよう、
ファイル名ではなく描画された内容からテキストを選んでください。
ビューアーやサンドボックスの変更は、Developer ID で署名されたサンドボックス化ビルドを使って、
Finder で複数のファイル系統にわたって確認する必要があります。サンドボックス外での WebKit の
テストや署名の検証だけでは、プレビューが動作することの証明になりません。
単体のフォームとプロジェクト内のフォームの両方を試してください。CLI で描画できても、Finder では
隣接する CSS、ポインターの参照先、ピクチャーへのアクセスが拒否されることがあります。
開発ビルドの最終確認では、Finder で両方のケースを描画し、4 つの外観の切り替えをすべて操作し、
ページを切り替えました。欠けているプロジェクトリソースは、キャンバスの前に警告として表示されました。
検証した macOS 26.7 のホストでは、ロック解除後も `qlmanage -p -o` が ExtensionFoundation 内で
辞書のキーが nil のため異常終了しましたが、実際の Finder のプレビューとコントロールは動作しました。
ハーネスはこのエクスポートツールの失敗をレンダラーの失敗とみなさず、Finder を使います。

カタログの入力・フォーカスの回帰確認には、次を実行します。

```sh
swiftc scripts/finder-preview-focus.swift -o build/finder-preview-focus
build/finder-preview-focus Tests/FourDFileKitTests/Fixtures/catalog.4DCatalog
```

既存の Quick Look を閉じて指定のカタログを開き、ネイティブの Control スクロール、
リセットの最初のクリック、ズームインの最初のクリック（120%）を確認します。
Quick Look を開いたまま一時的なテキストファイルとフォルダを選択し、
カタログに戻るたびに同じ確認を繰り返します。結果は JavaScript や
アクセシビリティのボタン操作ではなく、アクセシビリティの表示値で判定します。
ロックされていないデスクトップ、オートメーションとアクセシビリティの許可、
意図した拡張機能の登録が必要です。実行中は他のアプリを操作せず、Finder を
最前面に保ってください。物理トラックパッドのピンチは合成しません。
AppKit テストでは、非キーウインドウへの再接続と、位置・サイズを変更した子ビュー内の
ネイティブ拡大イベントの座標も確認します。ただし、Finder のリモートプレビューや
物理トラックパッドの確認を代替するものではありません。手動確認では、初回表示の
ボタンとスライダーに加え、ファイル・フォルダの選択切り替え前後のピンチを確認してください。

## ファイル形式に関するメモ

コンテナ形式は
[miyako/DataAnalyzer](https://github.com/miyako/DataAnalyzer)（JPR による 2015 年の
テクニカルノートに基づく）に由来し、実際のファイルで検証しています。オフセットは、それを読む
コードの横にソースコード内で記述されています（`DB4DHeader.swift`、`DB4DContainer.swift`、
`DB4DCatalog.swift`）。知っておくべき点:

* `.4DB` は `.4DD` と同じコンテナを使用します。ユーザーテーブルはどちらでも TDEF
  ブロックで定義されます。`.4DB` 自身のストレージには 2 つのシステムテーブル
  （リソース用の `Res_DB4D_000000` とスキーマ用の `sch_DB4D_000000`）があります。
* データファイルにはテーブルの過去の定義がすべて残っています。最後に書き込まれたものが
  現在の定義で、これはテストの `catalog.4DCatalog` と一致します。
* フィールド型コードはカタログの `type` 属性です。型 10 は、文字数制限が設定されていれば
  文字（Alpha）、そうでなければテキストです。
* ヘッダーの言語（dialect）フィールドは Windows の LCID です（1041 = 日本語、1036 = フランス語）。
* ヘッダーのデータベース UUID は、ストラクチャファイルとそのデータファイルで同一です。
* 追加プロパティ（xDAT）はシリアライズされた値の集合です。`ValueBag.swift` のデコーダーは
  リバースエンジニアリングによるもので、認識できないものに出会うと安全に停止します。
* 暗号化（`Encrypt data file`、v17 R5 以降）は、暗号化可能に設定されたテーブル
  （テーブル定義の +202 バイト目）のレコードと BLOB にのみ適用されます。それらのブロックは
  平文のヘッダーを保持しますがタグが変わり（`rec1` → `recx`、`blob` → `blbx`）、
  プレビューは各テーブルの最初のレコードから実際の状態を読み取ります。テーブル定義、
  レコード数、ヘッダーは暗号化されません。暗号化されたファイルには
  `encryptedProofB64` 追加プロパティ（キーチェック値）も加わります。
  データキーが必要になることはなく、入力を求められることもありません。

リレーション（`[Table_1]Field_4 → [Table_2]ID`）はデコードされ、`.4DB` 内の
リソースタイプも数えられます（`fourdql --json --thorough`）が、プレビューには
どちらも表示されません。

未デコードの項目: 件数以外のインデックス定義、レコードの中身、
ほとんどのリソースタイプの意味。

カタログ XML の規約と図の表示は
[miyako/4d-catalog-diagram](https://github.com/miyako/4d-catalog-diagram) と
[miyako/4d-utility-structure-to-svg-converter-v2](https://github.com/miyako/4d-utility-structure-to-svg-converter-v2)
を参考にしています。
リレーションの端点と主キーは、まず UUID で、次に曖昧さのない名前で解決されます。
未知のフィールド型は `Type n` と表示され、未知の XML 要素は無視され、
解決できない参照はパーサーのメモに報告されます。カタログの `encryptable` フラグは
ストラクチャの設定を表すもので、特定のデータファイルの暗号化状態を表すものではありません。
